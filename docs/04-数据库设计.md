## 0. 约定

- PostgreSQL 15；表名及主键以迁移为准。多数表使用 bigint 自增 ID；project_plan_baselines 以 project_id 为主键，bot_conversation 使用单数表名。日期用 date，事件时间通常为 timestamptz。
- 各表外键、索引和删除行为按迁移逐项定义；不能仅凭字段名为 *_id 就推定存在数据库外键。
- bigint id 在 JSON 序列化时为字符串，前端匹配一律 `String(a.id)===String(id)`。
- 表结构一律由 **TypeORM Migration** 管理（`synchronize` 默认关闭）：改实体/SQL模型 → 新建或生成迁移并逐条审核 → 测试 → 构建 → 启动执行未应用迁移。部分表直接由 SQL migration 管理，自动生成不能代替人工检查。见 [部署说明](08-部署与运维方案.md)。
- 父任务（有子任务）不设自身 `start_at`/`due_at`，展示时间范围由子任务最早开始~最晚结束派生。

### task_assignees（多执行人/多负责人）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| task_id | bigint | |
| role | varchar | `assignee` 执行人 / `acceptor` 负责人 |
| user_id | bigint | 用户 |

唯一索引 (task_id, role, user_id)。**一个任务可有多个执行人、多个负责人**。

**任务状态机**：

| 当前状态 | 允许转入 |
|---|---|
| pending_confirm | todo / rejected / cancelled |
| todo | doing / cancelled / pending_confirm |
| doing | pending_accept / cancelled / todo |
| pending_accept | done / doing / cancelled |
| done | doing（仅管理员或总经办负责人，需原因） |
| rejected | todo / cancelled |
| cancelled | 无 |

状态映射只是第一层检查；操作还受人员、计划定稿、结项冻结、周进展和资料完整性约束。见 [状态机实现](../server/src/modules/tasks/task-state.ts)。

## 2.6 jsonb 结构

**project_templates.skeleton**（阶段→子任务骨架）：
```json
{ "tasks": [ { "title": "一、项目筹备与启动", "durationDays": 45, "children": [ { "title": "项目组建", "durationDays": 10 }, … ] }, … ] }
```

**plan_change_items.before / after**（按 change_type）：
- `date` → `{ startAt, dueAt }`
- `add` → `{ title, startAt, dueAt, assigneeIds[], acceptorIds[] }`（task_id=父阶段或 null=顶层）
- `assignee` → `{ assigneeIds[] }`；`acceptor` → `{ acceptorIds[] }`
- `reorder` → `{ sortOrder }`

**project_closures.snapshot / report**：申请事实快照与批准后固定报告数据，包含当时项目、任务、进展、资料、审批及相关依据；不读取实时任务冒充历史报告。

## 3. 说明

- tasks.is_lagging 为兼容字段；当前风险展示还按日期、状态及子任务递归计算，不能只依赖该列判断风险。
- 任务总进度**不落表**，查询时按状态折算 + 子任务汇总现算（数据量不大，性能足够；要缓存可在 task 加 `progress_cache` 加触发刷）。
- 结项快照与报告用 jsonb 留存；重开仅标记旧版本失效，不重写报告正文。
- archived_projects、feishu_webhooks、system_config 是旧设计设想，当前迁移不创建这些表。

## 4. 结项与报备表

以迁移 `1789603200000-AddProjectClosures.ts` 为准，新增 `projects.closure_state`（none/pending/closed）、`project_closures`（申请及批准后固定报告）、`closure_notices`（投递、知晓／已阅状态）、`project_delay_records`（不可覆盖的延期事实）和 `closure_access_logs`（导出／下载记录）。

当前使用 project_closures 留存。批准结项后以 `status=archived, closure_state=closed` 保持原列表兼容；历史归档保持 `closure_state=none`。新增留档表不级联删除，业务接口阻止删除已结项项目。申请、报告与通知均保留事件当时的信息快照，确认状态单独记录。

2026-09-18 增量迁移 `1789689600000-CompleteClosureWorkflow.ts`：首次定稿快照 `project_plan_baselines`、重开审批 `closure_reopens`、HR 阅览授权 `closure_hr_grants`、台账及历史补填核查处理记录 `closure_followups`。结项申请新增 withdrawn/voided 状态；重开批准只标记旧报告失效，不改正文。历史项目基准明确未知，新项目第一次定稿原子留存。详细字段与权限见 closures 模块 README。

## 5. 资料、周进展与迁移关系

- `1800100000000-AddTaskMaterialExemptionReason.ts`：`tasks.material_exemption_reason` 可空文本，保存当次无资料提交验收原因，退回后清空，历史完成任务不回填。
- `1800300000000-AddProgressNoMaterialReason.ts`：`task_daily_updates.no_material_reason` 可空文本，保存每条进展的无资料原因；应用限制 1–500 字。新建/编辑进展须本条有资料或有原因，历史数据不回填。该字段与合理补填的 `exempt_reason`、任务验收的 `material_exemption_reason` 分开使用。
- `1800200000000-AddWeeklyProgress.ts`：`weekly_progress_settings` 记录首次启用时刻，不追溯更早周；`weekly_progress_checks` 按任务、周唯一，保留缺失/补齐/暂停提醒、实际提交时间和迟填状态；`weekly_progress_deliveries` 按渠道、接收目标、周唯一，记录已成功通知的检查 ID，失败可重试，同周新增缺失项增量通知。
- 上述迁移随后端部署执行。测试只能在隔离 schema 使用假通知；不需修改正式人员 ID 或重置历史任务。

### 已有资料复用
- 一份资料保留一条 task_assets 记录。多个进展可以关联同一文件或链接，任务/项目/结项报告的资料总数按资料记录去重。
- 新迁移 AddSharedProgressAssets1800400000000 添加 linked_daily_update_ids，默认空数组；旧 daily_update_id 和文件路径保持兼容。
- 关联、解除关联、删除进展通过任务行锁串行化并与操作日志同事务提交。解除关联或删除进展仅清理对应引用，不删除文件；共享资料禁止直接整体删除。

## 6. 机器人数据

- bot_query_logs：查询身份、原文、意图、结果与错误；agent_trace（jsonb）保存工具调用追踪，已由 1789000000000-AddBotAgentTrace.ts 加入。
- bot_conversation：1800000000000-AddBotConversation.ts 创建，保存用户/助手对话供追问上下文使用；不是尚未落地的规划表。
- 初始查询日志表来自 1788246000000-AddBotQueryLogs.ts。

## 7. 维护及部署核验

完整字段、默认值、索引和 SQL 约束以 [实体目录](../server/src/entities/) 和 [迁移目录](../server/src/migrations/) 为准，本文为业务数据字典，不宣称所有 ID 字段均有外键。结项扩展和周进展中有直接 SQL 管理的表，应同时核对迁移，不能仅统计实体数量。

上线后对照 migrations 表与发布包中的 dist/migrations；不要用本文旧版的固定“表总数”判断迁移成功。报告背景、目标及成果存入结项 JSON 快照，不应自行在生产补列。

### 结项材料、审核快照与智能解析

- 迁移 `1800500000000-AddClosureApplicationFiles.ts` 新建 `closure_application_files`：id、project_id、uploaded_by、original_name、file_path、file_size、created_at；project_id 有索引和 `ON DELETE CASCADE`，用于清理可删除项目的草稿文件记录，不改变正式结项留档表的保留策略。物理文件位于 `uploads/closure-charters`。
