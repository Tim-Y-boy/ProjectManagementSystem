## 0. 约定

REST + JSON，前缀 `/api`。鉴权：`Authorization: Bearer <jwt>`。统一响应：

```json
{ "code": 0, "data": {}, "message": "ok" }
```

- 成功：`code=0`，`data` 为业务数据。
- 业务错误：`code != 0`，`message` 给可读原因（如"项目计划已定稿，请发起变更申请"）。
- 分页不是全局统一契约。操作日志使用 page/pageSize，另有 limit 兼容参数；其它列表依对应 Controller/Service 返回结构，不承诺统一 list/size。
- HTTP 401 = 登录过期（前端跳登录页）；403 = 权限不足；500 = 服务端异常。
- bigint id 可能序列化为字符串，前端匹配用 `String()` 比较。

## 4. 任务

| Method | Path | 权限 | 说明 |
|---|---|---|---|
| GET | `/tasks` | 按可见性 | 列表，支持 project/dept/assignee/status/date 多筛选；`mine=true` 只看我参与的（执行人/负责人/创建者）；`parentId=all` 返回全部含子任务 |
| GET | `/tasks/:id` | 按可见性 | 详情含日志、children、多执行人/多负责人 |
| POST | `/tasks` | 按新增权限 | 创建。body 含 `projectId`、`parentId`(父子层级)、`assigneeIds`(执行人)/`acceptorIds`(负责人)；admin/leader 可在全部未定稿项目新增，dept_head 可在可管理部门未定稿项目新增，普通员工仅可在自己负责的未定稿项目新增；`acceptorIds` 为空时默认项目负责人 |
| PUT | `/tasks/:id` | 执行人/创建者/项目负责人/dept_head(本部门)/leader/admin | 改标题/说明/截止/执行人/负责人等（多执行人/多负责人全量替换） |
| POST | `/tasks/:id/confirm` | admin/leader/dept_head，再检查任务部门权限 | 审核通过 todo |
| POST | `/tasks/:id/reject` | admin/leader/dept_head，再检查任务部门权限 | 退回 rejected |
| POST | `/tasks/:id/transition` | 执行人/负责人/创建者/项目负责人/leader/admin | body `{to}`，状态流转，校验合法性 |
| POST | `/tasks/:id/reassign` | leader/dept_head(本部门)/admin | body `{assigneeId}`，改派，记log |
| DELETE | `/tasks/:id` | 按任务删除权限 | 仍受计划定稿、归档及结项冻结检查，不存在“任意态绕过” |

> 项目定稿后，`POST /tasks`、`PUT /tasks/:id`、`DELETE /tasks/:id` 会被拒绝（需走计划变更申请）；已定稿项目的 `transition` 状态流转不受计划改动锁影响。

> 任务列表新增任务时，前端只展示当前用户负责的项目；从项目/父任务行进入新增时，项目负责人会自动带入任务负责人，减少重复选择。

> 执行前置：项目未定稿时，`transition` 到 doing/pending_accept/done 会被拒绝；关键进展和过程资料也不允许提交。

> 父任务规则：有子任务的父任务不允许手动开始、提交验收或验收；由子任务状态自动汇总。

> 验收卡点：提交 pending_accept 与验收通过 done 均核查缺填周次，并要求有效资料或无资料原因，见下文“每周进展验收校验”。

**transition 合法映射**（后端校验）见 04 状态机。

> `DELETE /projects/:id` 仅 admin 或任一项目负责人；项目须未定稿、未归档且未结项冻结。

**任务父子树**：`POST /tasks` 传 `parentId` 建子任务；`GET /tasks/:id` 返回 `children` 递归树 + `hasChildren`；进度**父任务=子任务进度汇总，叶子=状态折算**（todo=0、doing=50、pending_accept=90、done=100）。

### 4.1 关键进展

| Method | Path | 权限 | 说明 |
|---|---|---|---|
| GET | `/tasks/:id/daily-updates` | 按可见性 | 任务关键进展列表，返回时每条带关联资料 |
| POST | `/tasks/:id/daily-updates` | doing/done 任务参与者/管理者 | 兼容新增入口，无附件时必须传 `noMaterialReason`；新前端统一使用 `progress-save` |
| POST | `/tasks/:id/progress-save` | 任务参与者/管理者 | 进展与资料原子保存，multipart 格式详见文末 |
| POST | `/tasks/:id/daily-updates/:updateId/exempt` | 可管理该项目（admin/领导/部门负责人可管该项目/项目负责人） | 将某条进展标记为豁免，body `{reason}` |

校验：

- 任务必须是叶子任务；
- 项目必须已定稿；
- 任务必须处于 `doing` 或 `done`，项目不能归档或结项冻结；
- `content` 必填，每条进展必须有资料或无资料原因。

### 4.2 过程资料

| Method | Path | 权限 | 说明 |
|---|---|---|---|
| GET | `/tasks/:id/assets` | 按可见性 | 任务资料列表 |
| POST | `/tasks/:id/assets` | doing/done 任务参与者/管理者 | 登记飞书文档/多维表格/外部链接资料 |
| POST | `/tasks/:id/assets/upload` | doing/done 任务参与者/管理者 | 上传本地文件，`multipart/form-data`，单文件最大 50MB |
| GET | `/tasks/:id/assets/:assetId/download` | 按可见性 | 下载本地上传文件 |
| GET | `/tasks/:id/assets/:assetId/preview` | 按可见性 | 预览本地上传文件；文本/Markdown/JSON/CSV 等返回 UTF-8 inline，图片可浏览器直接预览 |
| DELETE | `/tasks/:id/assets/:assetId` | 按权限 | 删除资料并写操作日志 |

校验：

- 新资料必须传 `dailyUpdateId`，即必须关联某天关键进展；
- 链接资料必须有 `url`；
- 本地上传必须有 `file`；
- 前端录入进展时一并保存文件/链接；已有进展可通过“补资料”继续添加，同一条进展可关联多份资料。
- 已验收任务允许继续补充关键进展和过程资料，用于完善验收证据。

## 6. 计划变更审批

| Method | Path | 权限 | 说明 |
|---|---|---|---|
| POST | `/plan-changes` | 项目可管理角色 / 项目任务执行人 | 发起申请（提交时按发起人定级：非项目负责人→先 owner 再 final；负责人本人→直接 final；终审人=总经办负责人） |
| GET | `/plan-changes` | 按可见性 | 列表，返回含 projectName/projectOwnerId/projectDeptId/stage/finalApproverId 等 |
| GET | `/plan-changes/:id` | 按可见性 | 详情（含 items、任务标题、审批轨迹字段） |
| POST | `/plan-changes/:id/approve` | 仅当前级：owner=项目负责人；final=终审人(总经办负责人)或管理员 | 通过：owner 级仅推进到终审（不生效）；final 级才应用全部变更 |
| POST | `/plan-changes/:id/reject` | 同上 | 退回（附意见；记录 rejected_stage，任一级退回整单退回） |
| DELETE | `/plan-changes/:id` | 发起人 | 撤销（仅 pending） |

审批链与字段详见 [12-计划变更审批](12-计划变更审批.md)。存量单（`final_approver_id` 为空）按原单级规则审批。

变更项 `change_type`：`date`(改日期) / `delete`(删任务) / `add`(新增任务，task_id 可为 null=顶层或父阶段 id) / `assignee`(改执行人) / `acceptor`(改负责人)。

**发起申请 body 示例**（顺延 3 天 + 改执行人）：
```json
{
  "projectId": "1",
  "reason": "设备到货延迟，中间节点延后 3 天",
  "items": [
    { "taskId": "5", "changeType": "date", "before": { "startAt": "2026-08-01", "dueAt": "2026-08-05" }, "after": { "startAt": "2026-08-04", "dueAt": "2026-08-08" } },
    { "taskId": "6", "changeType": "date", "before": { "startAt": "2026-08-06", "dueAt": "2026-08-10" }, "after": { "startAt": "2026-08-09", "dueAt": "2026-08-13" } },
    { "taskId": "5", "changeType": "assignee", "before": { "assigneeIds": [10] }, "after": { "assigneeIds": [10, 12] } }
  ]
}
```

## 11. 通知触发时机（后端内部，非API）

| 事件 | 动作 |
|---|---|
| 项目创建 | 不发送通知 |
| 项目计划定稿 | 给项目负责人推 `project_plan_locked_owner` 汇总卡片；给任务执行人/负责人推 `project_plan_locked_member` 个人任务汇总卡片；同一收件人合并发送 |
| 计划变更提交 | 推 `plan_change_submitted` 给当前审批级接收人，卡片突出变更项、任务名、前后值、原因 |
| 计划变更通过/退回 | 推 `plan_change_approved` / `plan_change_rejected` 给申请人，卡片展示审核结果和已应用/未应用的变更 |
| 任务提交验收 | 推 `task_submitted_acceptance` 给任务负责人 |
| 任务验收通过/退回 | 推 `task_acceptance_approved` / `task_acceptance_rejected` 给执行人/相关人 |
| 每日汇总（今日待处理） | 每天 09:10、13:10 给当天「有事」用户推 `daily_digest_0910` / `daily_digest_1310`；**周六日与法定节假日停发**（依 `holidays` 配置判断，调休补班的周六日照常）；「待办」中未开始任务仅距开始 ≤5 天或已临期/延期时提醒，无开始日期且无风险的任务静默 |
| 手动触发每日汇总 | admin/leader 调 `POST /notifications/due-soon/run` 推 `daily_digest_manual`（休息日也可手动触发，用于测试通知链路）；body 可带 `{ userId }` 仅给指定用户补发，避免打扰全员 |

推送结果落 notifications。短间隔重试、结项 outbox、周提醒补偿和卡片回写各有边界，不存在所有通知共用的无限重试队列。

## 12. 结项与报备接口

## 13. 进展原子保存与验收要求

- 前端通过 `POST /tasks/:id/progress-save` 一次保存关键进展与资料（multipart：`payload` 为 JSON，`files` 可多份）。`payload` 包含 `workDate`、`content`、`noMaterialReason`、`links: [{title,url}]`；编辑传 `updateId`，仅补资料另传 `materialsOnly: true`。进展、资料与日志同事务保存，失败保留前端完整草稿，服务端回滚并清理本次上传。
- 每条新增或编辑的进展必须有本条有效资料，或填写 1–500 字的无资料原因；其他进展及未关联资料不能替代。原因随进展返回展示，与合理补填原因、任务无资料验收原因分别记录。旧 `daily-updates` 新增/编辑接口同样检查；没有原因时不能删除本条最后一份有效资料。历史记录不强制回填。
- 上传单份最大 50MB、每次最多 30 份且合计不超过 200MB；Web Nginx 请求限制 201MB（预留 multipart 开销）。
- `POST /tasks/:id/transition` 增加可选 `materialExemptionReason`。提交验收时必须已有任务文件/有效 HTTP(S) 资料链接，或使用关键进展中已保存的无资料原因（去重后生成验收快照，无需重复填写）；兼容旧客户端无已存原因时传入 1–1000 字原因。验收人可见原因并决定通过或退回，退回后清空验收快照，重新提交时再次从进展读取。
- 待验收阶段不允许删除验收资料。已完成历史任务不强制补录；退回后重新提交按新规则检查。
- `GET /dashboard/weekly-progress` 返回当前执行人的周进展缺失待办；任一执行人填写对应周的关键进展即可满足该任务要求。通知使用既有个人飞书消息卡片与已配置项目群，不创建飞书原生任务。

### 每周进展验收校验

- 登录用户可调用 `GET /tasks/:id/weekly-progress-missing` 预检，返回 `{ missingWeeks: [{ weekStart, weekEnd }] }`，按周起始日期升序；任务不存在返回 404。
- 提交 `pending_accept` 和验收通过 `done` 均在后端重新校验。存在缺填时返回 HTTP 400，错误体含 `code: WEEKLY_PROGRESS_MISSING`、`missingWeeks` 和可读 `message`；不改变状态、不写流转日志、不发送验收通知。
- 验收直接读取状态历史和关键进展，按实际 doing 区间与工作日的交集计算应填周次，不早于规则启用及任务创建时间；计划日期不产生应填周次，也不截断延期执行。等待验收不新增周次，退回后重新计入执行。包含当前周，纯休假周不要求。
- 日常提醒固定每周五 14:00，节假日跳过，不顺延；验收与提醒共用实际执行周次规则，但取消周五时间门槛，不依赖通知是否产生。
- 按填写的工作日期归属周次，任一执行人填写非空进展即满足该周。第三周进展不能替代第二周；补填后可重新提交，删除最后一条达标进展会恢复拦截。
- 电脑端和手机端显示全部缺填周次；“去补填”打开进展表单并预选最早缺填周日期，仍由用户选择实际工作日。待验收任务发现缺填时提示先退回补充，不提供绕过按钮。
- 填写进展时，工作日期旁显示“任务第 N 周”和日期范围，计划开始日期所在周为第 1 周，随工作日期变化；日期范围最多显示至任务截止日期；计划开始前、任务截止后及未设置计划开始日期时展示对应说明，不生成虚假的周次。

### 关联已有资料
- POST /tasks/:id/progress-save 的 payload 新增 existingAssetIds: number[]（可选，最多 100 份，自动去重）。创建进展、编辑进展和 materialsOnly 模式均支持；关联后的有效资料可满足本条进展的资料必填校验。
- 只允许选择当前任务的有效文件或 HTTP(S) 链接，服务端复核权限及任务状态。资料复用不复制文件或新增资料行，旧关联保留；关联和进展同事务保存，失败回滚。
- DELETE /tasks/:id/daily-updates/:updateId/assets/:assetId：仅解除这条进展的资料关联，保留原资料和其他引用。若为该进展最后一份有效资料且未填写无资料原因，则拒绝解除。
- 任务资料返回 linkedDailyUpdateIds，连同 dailyUpdateId 表示全部关联；任务与项目进展列表的 assets 包含复用资料。多个进展共享的资料必须先解除关联，不能直接整体删除。
- 前后端需一并发布，后端启动自动执行新增迁移。

接口权限应同时核对 Controller 守卫与 Service 的人员、状态和冻结检查；尤其任务验收仅指定验收人或 admin/leader，已完成退回仅 admin/总经办负责人。

结项提交契约以 [结项模块接口说明](../server/src/modules/closures/README.md) 为准。新申请传背景、目标、成果、立项书或无立项书说明及 `scope`，服务端重算部门审核集合；不再使用 `reviewerIds` 决定新申请的审核人。`/:id/transfer` 仅保留历史 version=2 兼容。新增规则配置、异步解析及草稿接口见模块说明。


## 14. 工作日报与统一审批查询

| Method | Path | 契约 |
|---|---|---|
| GET | /dashboard/daily-report-status | 返回 canView/date/unreadCount/unreadDates；有权用户首次访问会初始化未读起点 |
| GET | /dashboard/daily-report?date=YYYY-MM-DD | admin 或当前总经办接收人；缺省上个工作日，日期不能晚于今天；查询成功写入已读 |
| GET | /approval-records?view=history | 本人实际处理的审批记录 |
| GET | /approval-records?view=mine | 本人发起记录 |
| GET | /approval-records?view=related | 参与关系及快照范围内记录；其它 view 返回 400 |
| GET | /task-approval-detail | taskId 或 logId 定位，kind=confirm/accept，at 可定位消息时点；返回 submitted/decision/status/canReview/isCurrent 等 |
| GET | /operation-log-projects | admin/leader/dept_head；操作日志项目选择项，可包含留有日志的已删除项目 |

网页 query 的 taskLogId 映射到 API logId，不要把两个字段混用。审批列表 path 保留具体事项参数；历史查看不能触发审批。待我审批来自待办及结项数据，不使用 approval-records 的 pending view。

工作日报按北京时间的原始提交时间 created_at 汇总，默认上一个工作日；工作日期 work_date 单独显示，不能把补填误当成当天完成。网页仅 admin 或当前总经办接收人可看，普通 leader/dept_head 身份本身不授予权限。读取日报成功后按用户与日期记录已读，未读从首次可见日期开始，不依赖本机浏览器缓存。
