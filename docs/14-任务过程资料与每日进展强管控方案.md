# 14 · 关键进展与过程资料

更新日期：2026-10-27。状态：当前本地代码已实现；线上是否具备对应功能，须核对发布版本及迁移记录。

## 1. 填写与编辑

任务详情使用同一个“进展与资料”页签。填写实际工作日期、关键进展，并上传文件、粘贴链接、选择飞书文件或关联已有资料，一次保存。资料名称从文件或链接获取，无需重复填写。

- 项目已定稿、未归档且不处于结项审批中/已结项状态，任务为有效叶子任务且状态为 doing 或 done，才可维护进展资料。
- 任务参与者、项目负责人及有维护权限的管理者可填写。编辑进展正文与新增权限不同：doing 状态下，作者、admin/leader 或 canWriteDept 命中者可修改；已确认合理补填的记录不可直接改删。done 状态仅 admin 可删除清理，不允许编辑正文；项目冻结及引用完整性检查仍适用。详见 [权限模型](03-权限模型.md)。
- 工作日期用于说明哪天做的；提交时间由系统记录，编辑不把原提交时间变成工作日期。
- 前端关键进展输入框限制 800 字；当前后端要求正文非空，但未另设 800 字上限。正文输入框支持约 6–16 行自动增高；电脑双栏下左侧编辑区保持在滚动视野内，表单过高时内部滚动。窄屏按上下结构展示，点击编辑会定位表单。
- 新建或编辑每条进展，必须具备本条有效资料，或填写 1–500 字的无资料原因。其他进展的资料不自动替代本条资料。
- risk、next_plan、affect_due_date 保留历史兼容；当前表单不要求再填写“问题/下一步计划”等独立字段。

## 2. 文件与链接

| 方式 | 使用说明 |
|---|---|
| 上传文件 | 单个最大 50 MB；每次最多 30 个，总计 200 MB |
| 粘贴链接 | 每行一个有效 HTTP(S) 地址；不直接保存任意脚本协议 |
| 选择飞书文件 | 选择可访问文件后保存链接；读取权限仍由飞书控制 |
| 关联已有文件/资料 | 选择同一任务已经登记的文件或链接，不重复上传；每次最多 100 个已有资料 ID |

一份资料可以关联同一任务的多条进展。任务、项目和结项报告统计资料份数时按资料 ID 去重，不按引用次数累加；不支持把其他任务的资料 ID 直接关联进来。

“解除关联”只移除当前进展的引用，保留文件及其他进展的引用。删除进展同样清理引用，不等于删除文件。共享资料不允许直接整体删除；没有无资料原因时不能移除本条最后一份有效资料。待验收阶段不能删除验收所依据的资料。

文件下载/预览通过带权限检查的接口完成。导出的 HTML 报告保留资料链接，不把附件内容打包进 HTML；转发报告不授予附件访问权限。

## 3. 提交验收

提交验收及验收通过时，后端都会核查实际执行周次。按操作日志重建 doing 区间，只检查不早于规则启用时间和任务创建时间、且与工作日相交的周次；计划日期不产生应填周次，也不截断延期执行。验收包含本周，不受周五 14:00 的提醒门槛限制。

资料要求为任务已有有效资料，或已保存的无资料原因。系统可从进展原因生成本次验收说明，避免重复填写；兼容旧客户端传 materialExemptionReason（1–1000 字）。退回后清空当次验收说明，下次提交重新读取。历史已完成任务不强制回填；退回后重新提交按当前规则检查。

完整周次规则与提醒边界见下文“周进展提醒与验收检查”。

## 4. 合理补填

“补填”描述录入时间，“合理补填”需要有权限的人确认。确认必须同时满足：

1. 有效工作日期不晚于任务截止日期；
2. 原始提交时间换算为北京时间日期后，晚于任务截止日期；
3. 截止、工作日期及提交时间均有效。确认原因可不填，填写时不超过 4000 字。

截止前或当天提交无需确认；工作日期已经超过截止则不能标为合理补填。管理员同样不能绕过这些条件。标记后向总经办发送知晓告知；知晓不是审批。撤销标记产生更正告知。

任务完成分类还要综合本任务其他进展，不因一条标记就豁免全部任务。结项报告仅在所有记录满足日期/确认条件时单列合理补填；不符合当前条件的旧标记保留历史记录，不能据此推定按期。系统验收时间与实际工作日期分别展示，不能把录入晚直接当成工作晚。

## 5. 数据及接口

进展存于 task_daily_updates；资料存于 task_assets。无资料原因 no_material_reason、合理补填原因 exempt_reason、当次验收说明 material_exemption_reason 是三个不同字段。

新前端使用 POST /api/tasks/:id/progress-save（multipart）原子保存进展与资料。更新传 updateId，关联已有资料传 existingAssetIds。旧 daily-updates 与 assets 接口保留兼容及补资料用途，同样执行权限和资料完整性检查。

共享关联由 daily_update_id 与 linked_daily_update_ids 合并去重表示，变更通过任务行锁及事务提交并记录操作日志。具体请求格式见 [接口设计](05-接口设计.md)，迁移见 [数据库设计](04-数据库设计.md)。

## 6. 尚未实现的扩展

按业务影响自动评估进展质量、自动生成绩效评分、附件全文语义检索不属于当前功能。周提醒、飞书文件选择和已有资料关联已实现，不再列为后续计划。

## 周进展提醒与验收检查

提醒与验收使用相同的实际执行区间，但触发时间和用途不同。

### 1. 日常提醒（保留启用时间边界）

每个有效叶子任务在北京时间自然周（周一至周日）内，只要有工作日与实际 `doing` 状态区间重叠，就至少需有一条关键进展。`task_logs` 的状态流转用于重建区间，已完成任务的最后执行周仍计算；无流转记录的存量 `doing` 任务从启用时刻开始。迁移 `AddWeeklyProgress` 记录启用时间，只从启用当周且启用后发生的工作日计入，不追溯更早周。

进展按 `work_date` 归属周；任何合法提交人的非空进展都满足该任务该周，不要求每个执行人各填。保存实际 `created_at`，晚于该周周日提交标为迟填。删除或移走该周最后一条进展后，待补填再次显示。取消任务、变成父任务、已归档项目、结项审批中/已结项项目停止催填，审计行保留。`pending_accept`、`todo` 等暂不支持提交进展的状态保留欠报记录但暂不催填；恢复 `doing` 或进入 `done` 后显示。

通知固定在北京时间每周五 14:00 发送（Cron：`0 0 14 * * 5`）。周五在系统 `holidays` 中标为节假日则跳过，不顺延周一，也不改到补班周末。提醒本周截至发送时尚未填写的关键进展，以及仍未补齐、尚未成功通知的历史周记录；按所属周分别汇总。本周从周五 14:00 起进入待补填检查范围，整周无执行工作日不催。按周、个人收件人或目标群保存已成功通知的检查记录，重复扫描不重发。周五之后新增的可补填记录和投递失败记录在下一次周五通知时处理。未定稿项目暂不催填。读取 `GET /api/dashboard/weekly-progress` 仍刷新留档（不发送消息），因此查看待办不会在周一触发群提醒。

个人使用现有 `buildNotifyCard` 卡片，总群使用 `FEISHU_BRIEF_GROUP_CHAT_ID` 配置。项目标题加粗、项目间空行分隔；按实际父子关系缩进并编号（如 `1.1`、`1.1.1`），同一父任务只出现一次。只展示待补填任务及其祖先，祖先不计入待补填数量，也不提供补填链接。群通知通过飞书 `at` 元素 @ 项目的全部负责人，统一使用 `users.feishu_user_id`；无绑定信息时显示姓名。任务保留执行人及对应周的补填链接。沿用 `FEISHU_NOTIFY_DISABLED`、`FEISHU_GROUP_NOTIFY_DISABLED` 等既有通知保护。不调用飞书原生 Task API。多实例使用 PostgreSQL advisory lock 防止并发重复检查/发送，失败保留尝试记录供下次重试。飞书发送与数据库成功记录之间若进程崩溃，存在外部服务与本地记录无法原子提交的短暂重复风险。

接口只返回当前登录执行人的未满足记录：`{ items: [{ id, taskId, taskTitle, projectId, projectName, weekStart, weekEnd, assigneeNames, ownerNames, desktopPath, mobilePath }], total }`。ID 是字符串，日期是 `YYYY-MM-DD`。桌面 `/tasks?projectId=…&taskId=…&weekStart=…`，手机页面 `/mobile/task/:id?weekStart=…`（旧辅助函数 mobilePath 可能返回 /m/tasks/:id，不能直接当作已支持路由）。组件 `WeeklyProgressNotices` 接受可选 `mobile` 属性，自动刷新，没有“我已知晓”按钮。

### 2. 验收检查（与提醒共用实际执行周次）

提交待验收及验收通过时均重新检查，不依赖提醒调度是否执行。与提醒共用 `requiredWeeks`，验收检查只取消周五 14:00 的时间门槛。

- 按操作日志重建实际进行中区间；计划日期不产生应填周次，也不截断延期执行。等待验收不新增周次，退回后重新计入执行。
- 检查不早于规则启用时间和任务创建时间。迁移 `UnifyWeeklyProgressWindow` 将启用时间更新为部署迁移时刻，保留原时间，不追溯此前已结束的执行区间。
- 北京时间周一至周日分周，工作日与执行区间相交即要求一条；提交时包括本周，同周多次执行只算一次，纯休假周不要求填写。
- 以工作日期归属周次，任一合法提交人的非空进展满足该任务该周。其他周的记录不能替代，删除最后一条达标记录后重新拦截。
- 缺填返回 HTTP 400，code 为 WEEKLY_PROGRESS_MISSING，附 missingWeeks 和可读提示；状态、流转日志和验收通知均不推进。
- 电脑和手机显示缺填周列表，“去补填”预选最早缺填周日期，由用户选择真实工作日。待验收时发现缺填，先退回再补。

迁移停止历史缺填催办，保留检查和发送记录。每次收集先将旧缺填标为不再提示，再按源记录恢复仍应提醒的周次，避免旧提醒残留。迁移前已经完成且未重新执行的任务不会追溯催填。资料/无资料原因要求见 [进展与资料](14-任务过程资料与每日进展强管控方案.md)。

## 工作日报中的进展

工作日报按北京时间的原始提交时间 created_at 汇总，默认上一个工作日；工作日期 work_date 单独显示，不能把补填误当成当天完成。网页仅 admin 或当前总经办接收人可看，普通 leader/dept_head 身份本身不授予权限。读取日报成功后按用户与日期记录已读，未读从首次可见日期开始，不依赖本机浏览器缓存。

进展正文、上传资料和日报摘要不是三份独立业务记录。更新资料不等于重新提交工作日期；日报、验收及报告对时间采用不同含义，界面应分别标注。
