# 03 · 权限模型

更新日期：2026-10-27。依据：当前本地 Controller、Service 和前端入口；不代表服务器已部署。后端校验决定操作结果，隐藏按钮只改善操作体验。

## 1. 身份与关系

| 身份 | 来源及用途 |
|---|---|
| admin | 系统管理员；角色配置、解除定稿、历史归档恢复、HR 阅览授权等专属操作 |
| leader | 领导；跨部门管理，不自动拥有所有申请的终审权 |
| dept_head | 部门负责人；登录时可由 departments.head_user_id 推导，JWT 带 managedDeptIds |
| member | 普通成员；通过项目、任务参与关系取得相应操作权限 |
| 项目负责人 | projects.owner_id 与 project_owners；支持多人，任一负责人参与项目权限判断 |
| 任务执行人/验收人 | 主字段 assignee_id/acceptor_id 兼容旧数据，多人关系在 task_assignees |
| 结项指定审批人 | 申请提交时固定的 approver_id；不等同于任意领导或管理员 |
| HR 阅览人 | 报告接收人/当前 HR 负责人及 closure_hr_grants 授权人；阅览不授予审批权 |

一个人可以有多个角色。飞书部门负责人关系影响 managedDeptIds；手工角色与组织架构同步是不同来源，权限更新需获得新的登录态。

**实现边界**：tasks.service 的 canWriteDept 当前按 admin/leader、用户主部门或 managedDeptIds 判定，本函数本身没有再次要求 dept_head。各入口是否另有角色校验，应同时读取 Controller 和 Service；不能将“本部门可写”统一表述为“只有部门负责人可写”。本文记录实际校验，不把界面隐藏按钮等同于服务端授权。

## 2. 项目操作

| 操作 | 当前校验 |
|---|---|
| 创建项目 | Controller 仅允许 admin/leader/dept_head，再由 Service 校验创建权限。dept_head 可选择任意归属部门；创建不自动获得永久管理权 |
| 编辑项目 | Controller 仅允许 admin/leader/dept_head，再检查 canWriteDept 或项目负责人关系，以及项目冻结和字段限制；普通 member 即使是项目负责人，也会被此接口的角色守卫拦截 |
| 定稿 | admin/leader、canWriteDept 或任一项目负责人；不能操作归档/结项冻结项目 |
| 解除定稿 | **仅 admin**；不绕过结项冻结 |
| 删除项目 | **仅 admin 或任一项目负责人**，且未定稿、未归档、未结项冻结；leader 身份本身不赋予删除权 |
| 申请结项 | **admin 或任一项目负责人**；已定稿、有效任务全部完成、无待审批计划变更、未归档且 closure_state=none |
| 结项审批 | 前置阶段由申请快照中的部门负责人审核，全部通过后由指定总经办审批人终审；admin 不因身份自动获得审批权 |
| 结项审核规则 | admin/leader/dept_head，服务端复核数据库当前启用身份；配置变更不改写已提交申请 |
| 撤回结项 | 申请人，且申请仍待审批，原因必填 |
| 重开结项纠错 | 当前项目负责人申请；指定审批人审核；批准后旧报告失效并保留版本 |
| 恢复历史归档 | **仅 admin**；新结项及结项审批中项目不能使用此入口 |

项目已定稿后，计划修改走 [两级计划变更审批](12-计划变更审批.md)。状态流转及进展维护属于执行操作，仍受任务状态、人员关系及结项冻结约束。首次定稿计划留存不被后续解锁覆盖。

## 3. 任务操作

| 操作 | 当前校验 |
|---|---|
| 增删改计划 | 未定稿时按对应接口的管理/负责人权限；定稿后改日期、人员、层级、顺序及增删任务走计划变更 |
| 开始、提交验收、进行中恢复待办 | 执行人、创建者、项目负责人、验收负责人或 admin/leader，按合法状态流转检查 |
| 待验收通过/退回 | 指定任务验收负责人或 admin/leader；部门负责人身份本身不自动成为所有任务的验收人 |
| 已完成退回进行中 | **admin 或总经办负责人**，退回原因必填；项目不能归档或结项冻结 |
| 填写进展/补资料 | admin/leader、canWriteDept、项目负责人或任务参与者；任务须为 doing/done 的有效叶子任务，项目须已定稿且可编辑 |
| 编辑/删除进展 | doing 状态下，作者、admin/leader 或 canWriteDept 命中者可操作；合理补填已确认的记录不可直接改删。done 状态仅允许 admin 删除清理，不能编辑正文；另检查项目冻结和资料引用 |
| 删除资料/解除关联 | 使用对应接口的人员、任务状态、有效资料及引用完整性校验，不能仅凭新增权限推导 |
| 确认/撤销合理补填 | 按项目管理权限及日期资格检查，原因和通知留痕；详见进展文档 |

有活动子任务的父任务由子任务自动汇总，不能手动开始或验收。提交与验收通过均核查周进展和资料要求，管理员不绕过完整性检查。

## 4. 计划变更审批

发起人可以是项目负责人、可管理项目的人或项目任务执行人。项目任一负责人发起时直接进入总经办终审；其他发起人先经项目负责人预审，再到终审。无负责人或负责人就是终审人时按服务端解析的审批链处理。

终审只允许单上终审人或管理员，不能用“领导可审批所有变更”概括。owner 阶段与存量 final_approver_id 为空的申请按对应兼容规则校验。撤销仅发起人且申请待审。与结项审批不同，**计划变更终审存在管理员权限**。

## 5. 读取与系统管理

- 登录用户可查看项目/任务基础信息；mine 筛选收窄为参与项目，不是统一后端隔离边界。待办、机器人涉他人查询、结项报告分别使用自己的权限规则。
- 真实员工和部门来自飞书；所有登录用户可查询基础信息供选人。分配角色、启停、批量角色和 Mock 部门维护仅 admin；Mock 角色固定。
- 全局操作日志入口面向 admin/leader/dept_head。单任务过程信息与报告附件仍按对应接口检查。
- 结项报告允许对应项目负责人、指定审批/通知接收人、当前总经办/HR 负责人、admin/leader 及有效 HR 阅览授权人访问；“确认已阅/知晓”仅对应收件人本人。
- KPI 自动评分及 Excel 报表未实现，不列入已实现权限矩阵。

## 6. 日报与审批记录

工作日报按北京时间的原始提交时间 created_at 汇总，默认上一个工作日；工作日期 work_date 单独显示，不能把补填误当成当天完成。网页仅 admin 或当前总经办接收人可看，普通 leader/dept_head 身份本身不授予权限。读取日报成功后按用户与日期记录已读，未读从首次可见日期开始，不依赖本机浏览器缓存。

审批 history 按实际处理人筛选，mine 按发起人，related 按项目负责人、任务参与人、审批参与及变更快照筛选，结项／重开还检查报告可读权限。读取历史详情不授予重新审批权；canReview 还要求当前轮次、待审状态、任务层级、项目冻结状态与操作人匹配。

## 7. 维护要求

ID 比较统一使用 String(id)，兼容 PostgreSQL bigint 字符串。项目多人负责人判断不能只比 owner_id。冻结校验覆盖管理员入口。新增权限文档必须注明“人员关系 + 状态条件 + 接口校验”，不要只按四种角色画宽泛的勾选表。
