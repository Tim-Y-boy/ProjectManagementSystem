# 21 · 项目结项审批与人力资源报备

更新日期：2026-10-27。本文描述当前工作区实现；发布情况须核对服务器版本。新申请按部门规则审核（workflow.version=3），绿色报告模板已接入。

## 1. 申请与审批

申请人可以是管理员或项目任一负责人，记录实际申请人。领导、部门负责人如果既不是管理员也不是项目负责人，不能仅凭职务代申请。

申请须同时满足：

- 项目 active、已定稿、closure_state=none；
- 至少有一个有效叶子任务，全部有效任务均完成，叶子任务验收时间完整且不在未来；
- 项目具有批准截止日期；
- 无待审批计划变更，能解析到唯一启用的总经办审批人。

项目完成条件通过后提交申请，不等于结项已经生效。提交固定终审人并冻结编辑；按部门规则确定的负责人先并行审核，全部通过后才交由**单上指定总经理（总经办负责人）**终审，管理员身份不自动获得结项终审权。申请人可填写原因撤回待审单。终审通过时复核任务依据，保存正式报告并通知相关人员。无新版 workflow 的历史申请维持原单级审批。

### 1.1 材料、智能解析与部门审核

- 上传立项书，或填写无立项书说明；背景、目标、实际成果必填。PDF/DOCX 解析复用现有 LLM 配置，只预填空白背景和目标，预期成果归入目标，实际成果始终人工填写；重新解析不覆盖非空正文。
- 默认八部门（含生产部），HR 固定必审，其他按可配置条件判断。本部门负责人及担任部门负责人的共同项目负责人必须审核；仅跳过实际提交人本人的前置节点，HR 同样适用。没有前置部门仍进入总经理终审。
- 有立项书时确认 AI 建议；“待确认”可保存草稿，不能提交。取消 AI 建议涉及的部门须二次确认，保存原建议与最终决定。无立项书时条件部门逐项回答“是／否”，默认未选；HR 无需勾选。切换有／无立项书后重新确认。
- 审核人取部门负责人，不能任意转交。同一人负责多个部门时一次处理其全部待审部门，分别保存责任与清单。通过须填齐清单，不适用须说明，不符合不能通过；退回可以不填完清单。退回重提重新审核。
- admin/leader/dept_head 可维护规则，服务端复核当前启用身份。配置保存递增版本，新分析立即采用；已提交申请保持配置、判断、人员和清单快照。
- 解析异步持久化，运行中相同请求去重。文件、规则、提交人、项目负责人或部门负责人变化使旧结果失效。扫描件暂不做 OCR，失败可手工填写。单份不超过 50 MB，PDF 不超过 150 页，总提取文本不超过 180000 字符。
- 负责人缺失、停用或与固定终审人冲突时，先修正组织配置，不能自由选人绕过。系统主动关联与本次文件、配置和身份一致的成功分析。

### 1.2 历史审批兼容

已有 version=2 申请保留自选审核人、转交和已通过结果沿用逻辑；转交不能给申请人、总经理或已有审核人。总经理退回后全部重新审核。无 workflow 的更早申请保持单级审批。上述兼容规则不用于新建 version=3 申请。

## 2. 审批、阅览和知晓

| 事项 | 操作 | 是否改变业务结果 |
|---|---|---|
| 结项前置审核 | 按规则确定的部门负责人通过/退回 | 全员通过后进入总经理终审 |
| 结项终审 | 指定总经办审批人通过/退回 | 终审通过后结项生效 |
| 合理补填告知 | 对应收件人“我已知晓” | 不改变补填标记，不是再审批 |
| HR 报告报备 | 对应收件人“确认已阅” | 不改变报告，不表示奖惩已执行 |
| HR 多人阅览授权 | 管理员配置全公司/指定部门范围 | 允许看/导出，不授予审批或代知晓 |

报告允许对应项目负责人、指定审批/通知接收人、当前总经办/HR 负责人、管理员及领导，并结合有效 HR 授权判定。普通项目列表可见不等于所有报告可见。

## 3. 时间与完成结论

| 日期 | 含义 |
|---|---|
| 工作日期 | 进展填写的实际工作日 |
| 填报时间 | 原记录创建时间；补资料不等于新完成任务 |
| 全部验收完成 | 全部有效任务完成后，取叶子任务最晚 completed_at |
| 申请结项 | 实际提交时间，不倒填 |
| 结项生效 | 审批通过时间 |

系统验收不等于实际完工。按北京时间自然日分别统计完成到申请、申请到审批的间隔。完成后达到 3 天才申请、申请/生效超过批准截止等情况自动提示，不强制用户另填说明，不依据天数自动定责。旧 delayReason/overdueReason 保留兼容，每项最多 4000 字。

当前任务报告按验收日期与截止比较，并检查全部进展的合理补填依据。只有全部记录都满足规则，才把该任务单列合理补填；缺少日期显示依据不完整。某条补填标记不清除整项目延期历史。

## 4. 冻结、重开与历史兼容

申请待审时 closure_state=pending；退回/撤回恢复 none；批准为 closed，同时 status=archived。冻结覆盖项目、任务、进展、资料与补填标记，管理员同样受限。

项目负责人可申请重开纠错，原因必填；指定审批人通过/退回均需意见。重开通过后原报告标记 voided，正文不改，恢复项目编辑，向原 HR 等相关接收人告知更正。再次结项生成新编号/递增版本。

首次定稿基准保存在 project_plan_baselines，不因重新定稿覆盖。旧项目无基准则显示缺失。历史归档不会自动生成新审批报告；旧 unarchive 仅管理员使用，不能解锁新结项。

## 5. 负责人待办、台账与合理补填

全部完成未申请的项目进入负责人待办和每日简报；提交后显示审批中，避免把等待审批误写成负责人未申请。重开或任务重新打开后重新核查完成条件。

延期台账保存当时截止、验收和观察日期；相邻日期的超期记录不是可累加的新延期。追加处理状态 open/processing/resolved 和说明不删除原事实，也不自动触发奖惩。

合理补填要求工作日期不晚于截止、原提交日期晚于截止，日期有效；确认原因可选，最多 4000 字。标记即生效并发送知晓告知，撤销另发更正。历史标记不符合当前日期规则时进入核查，不自动改写历史进展。

## 6. 报告与资料

报告按有效叶子任务统计，保留主子层级，资料按 ID 去重。在线和独立 HTML 共用报告渲染逻辑；读结项时快照，报告附件单独鉴权，导出 HTML 不含附件文件。历史报告保持原有总览、成果、延期/关键事项和折叠依据版式。

新申请使用已确认的四部分绿色模板：基本信息、项目背景与目标、项目执行情况、项目成果，正文后附审核记录。自然语言背景/目标/成果与立项依据随申请保存。不能将示例指标或“确认实际完成日期”写成系统已有字段。去掉问题与经验、结论与后续安排等章节的要求记录在模板说明中。

## 7. 配置与可靠性

总经办接收人由 PLAN_FINAL_APPROVER_USER_ID 或 PROJECT_GM_DEPT_NAME 解析；HR 由 PROJECT_HR_NOTIFY_USER_ID 或 PROJECT_HR_DEPT_NAME 解析。ID 是当前环境的本地用户 ID，不写死具体人员。不能解析总经办会阻止申请/补填告知；HR 未配置保留待配置状态，后续补发。

业务事务写 closure_notices，后台投递尝试记 notifications；投递与确认分开。网络成功而本地回写失败可能重复触达，系统事件按键和收件人去重。审核完成会尝试更新原飞书审核卡片，不能以旧卡片按钮判断当前业务状态。

接口、存储、测试方式见 [结项模块说明](../server/src/modules/closures/README.md)；通知调度见 [飞书通知](06-飞书对接.md)。系统只提供事实、审批与处理记录，不自动计算 KPI 或奖惩。

## 留档、导出与 KPI 边界

结项留档已实现；KPI 计分与 Excel 报表未实现。

### 1. 当前留档方式

项目采用结项申请与审批，不再直接归档。管理员或任一项目负责人在满足完成条件后申请，经部门负责人审核后由指定总经办负责人终审。申请冻结项目，退回/撤回恢复编辑，批准后固定报告并报 HR 阅览。详细规则见本篇申请与审批部分。

当前使用 project_closures.snapshot/report，不创建旧设计中的 archived_projects。批准后 projects.status=archived、closure_state=closed；历史旧归档的 closure_state=none，不伪造审批或自动补发报告。

历史旧归档仅管理员恢复。新结项需要项目负责人申请重开纠错，指定审批人批准后恢复编辑，旧报告标记 voided 并保留，再次结项递增版本。

### 2. 数据取证口径

- 首次定稿计划存 project_plan_baselines，后续解锁及变更不覆盖。历史项目没有基准时明确缺失。
- 工作日期、原始提交时间、系统验收时间、申请和审批时间分别记录；验收时间不能冒充实际完工日期。
- 延期事实存 project_delay_records，不因变更截止或确认某条合理补填而删除。
- 父任务不与叶子任务重复计入执行任务数；共享资料按资料 ID 去重。
- 符合全部依据要求的合理补填在报告单列，不将历史不合规标记当成按期证明。
- HR 已阅/领导知晓保存为独立状态，不修改固定报告，也不表示奖惩已经执行。

### 3. 已实现的导出

结项报告可导出独立 HTML，正文及内联图表可离线阅读。附件只保留链接，仍需系统或飞书授权，不随报告打包。导出及报告附件下载记录在 closure_access_logs。

当前没有通用任务 Excel 导出或 /kpi/report/export 接口。不要把浏览器打印、HTML 报告和 KPI Excel 导出混称为同一功能。

### 4. 待确认、未实现的 KPI 规划

以下仅供后续讨论，不参与当前权限或数据库设计：

| 候选指标 | 必须先确认的问题 |
|---|---|
| 按期完成率 | 采用工作完成还是系统验收日期；合理补填、取消与重开如何处理 |
| 任务完成量 | 仅叶子任务还是按成果；多人任务如何分摊 |
| 延期天数 | 计划变更、审批等待与个人责任如何区分 |
| 进展/资料完整性 | 资料份数是否有意义；无资料原因、共享资料如何计数 |
| 部门与个人评分 | 权重、复核、申诉及口径版本由谁确认 |

系统当前记录事实和处理说明，不自动定责、扣分、计算奖金或生成个人绩效结论。

## 报告模板与接入状态

示例中的项目、人员及数字不代表真实业务结果。

### 1. 当前确认模板

[报告渲染器](../server/src/modules/closures/closure-report-v2.ts) 实现四部分绿色模板，样式见 closure-report-v2-style.ts。主体四部分：

1. 基本信息：项目、计划日期、部门、负责人和执行人；参与名单不列职位。
2. 项目背景与目标：申请结项时由用户用自然语言描述，不要求额外考核指标表或范围表。
3. 项目执行情况：开头放任务完成分布及项目按期情况图表；保留主子任务层级，进度节点日期精确到日；交付资料表只保留系统可提供的序号、名称、类型。
4. 项目成果：由用户自然语言描述，不要求知识产权、经济收益、业务指标对比表。

已确认移除“问题与经验总结”和“结项结论与后续安排”。章节标题应突出，图表帮助领导及 HR 快速看到完成、按期、成果和关键延期点，不用无业务意义的资料数量长条或箭头串联独立记录。

### 2. 接入状态

上述模板已接入新结项申请与正式报告。背景、目标、成果由申请人补充确认并随申请保存快照；必传立项书或填写无立项书说明。不能把建项简略描述自动当成用户已经确认的结项总结。

系统由 server/src/modules/closures/closure-report.ts 按快照版本选择模板：workflow.version=2 或 3 使用 closure-report-v2.ts 及原版式绿色样式；旧申请、旧报告保留“项目总览、成果全貌、延期与关键事项、详细依据”。均支持在线阅读与独立 HTML 导出，使用结项快照。

新流程在四部分正文后增加审核记录，显示各审核人、结果、意见、日期与沿用来源，最后展示总经理终审。历史 version=2 详情另可查看审核转交记录；新申请不支持任意转交。未通过终审时展示申请预览，不能标为正式结项报告。

示例中的“确认实际完成日期”、示范收益和统计数字只用于设计展示。当前 completed_at 为系统验收时间，不应直接改名成实际工作完成日。接入时仍须遵守合理补填单列、父子任务不重复计数、共享资料按 ID 去重及附件独立授权等规则。

### 3. 模板维护

正式报告以申请快照和版本选择的渲染器为准；本地历史 HTML 仅为设计参考，不作为公开产品说明或真实业务数据。


## 当前页面和迁移边界

/closures（手机 /mobile/closures）是结项管理入口；closure-reports、closure-delays 为兼容重定向，接口中的台账与报告权限仍保留。审批待处理通过 /approvals 的具体 request 定位。

解析升级还需要 AddClosureAnalysisScopeIdentity：旧分析没有可靠 scope_identity 时视为过期，不能只修改最初迁移文件后假定旧数据库已升级。工作日报与 HR 延期日报是两个独立通知；前者面向总经办的提交进展，后者面向 HR 的当前未完成延期任务。
