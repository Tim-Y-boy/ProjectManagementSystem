# 06 · 飞书消息通知

更新日期：2026-10-27。当前实现通过企业自建应用发送消息，代码入口 FeishuNotifyService。登录与组织同步见 [接入手册](11-飞书接入实战手册.md)，卡片字段见 [消息格式](19-飞书通知消息格式.md)。

## 1. 通道与接收人

个人消息使用同步的 open_id 或 feishu_user_id；群消息使用 chat_id。通知落 notifications，记录 type、recipient_id、target、content、response、success、retry_count、关联业务 ID 及 sent_at。没有真实飞书身份的 Mock 账号不能证明真实触达。

项目负责人支持 project_owners 多人关系，任务执行/验收人支持 task_assignees。审批通知按当前审批阶段解析接收人，不能一律发给主 owner_id。角色、收件人及业务审批权限分别判断。

没有实现自动切换 Webhook 作为失败兜底，也没有通用的通知后台手动重发界面；手动汇总接口仅用于其对应业务。

| 类型 | 场景/对象 |

| task_completed_reopened / task_confirmation_rejected | 已完成退回/待确认退回 |
| project_delayed | 定稿后项目计划结束被推迟 |

## 3. 调度

使用 NestJS Schedule/Cron，下列带具体业务时刻的任务按 Asia/Shanghai；组织同步的 02:00 另按进程时区：

| 时间 | 行为 |
|---|---|
| 工作日 09:00 | 项目群简报（FEISHU_BRIEF_GROUP_CHAT_ID）及独立工作日报（当前总经办接收人） |
| 工作日 09:10 | 向已配置的 HR 负责人发送项目延期日报；按当日、接收人和分片去重 |
| 工作日 09:10、13:10 | 当天有待处理事项用户的个人汇总，按日/时段/人去重 |
| 每周五 14:00，节假日跳过 | 周进展填写提醒及未成功投递记录重试，按记录去重，不顺延至周一 |
| 每两分钟 | 结项通知 outbox 扫描；失败 30 分钟后再试 |
| 每分钟 | 原审核消息状态回写扫描，处理近 14 天记录 |

holidays 覆盖周末/工作日判定，调休补班照常发送。提醒与验收均按启用边界后的实际执行周次检查，验收不受周五提醒门槛限制，详见 [周进展](14-任务过程资料与每日进展强管控方案.md)。

POST /api/notifications/due-soon/run 由 admin/leader 手动触发个人汇总，可传 userId 限定对象。项目群简报使用 POST /api/notifications/project-brief/run；触发真实通知前核对目标，不把这些接口当普通只读检查。

## 4. 审核后更新原卡片

计划变更、任务验收、结项、重开审批完成后，系统异步尝试更新原消息为已审核/已退回/已撤回，并保留结果入口。预审通过显示已转终审，总经办卡片单独更新。任务多轮验收按原通知对应的首次结果关联，后续重提不改写旧审核结果。

发送时保存 reviewCard、reviewRef 及 message_id 到 notifications.response，不新增表列。回写失败不回滚业务审批，每分钟扫描近 14 天记录重试。旧消息缺少 message_id、关联不明确或平台不支持更新时，不能保证补写。

按钮打开系统处理，不是飞书卡片回调直接修改业务。合理补填“我已知晓”和 HR“确认已阅”也须登录，并只允许对应接收人确认。

## 5. 失败与配置

个人发送有有限次数的短间隔重试；结项与周提醒另有各自持久化补偿，不是所有消息共用一个无限重试队列。网络送达与本地记录不能原子提交，极端情况下可能重复触达。

- FEISHU_NOTIFY_DISABLED=true：禁止真实通知。
- FEISHU_GROUP_NOTIFY_DISABLED=true：禁止群通知。
- FEISHU_NOTIFY_REDIRECT_USER_ID：个人测试转发；无效时停止，不回退给真实审批人。转发不改变审批权限。
- WEB_FRONT_URL：按钮可达根地址，不能把本地 localhost 发给真实用户。

发版检查通知权限、账号身份、群成员资格与上述环境配置；配置清单见 [部署说明](08-部署与运维方案.md)。

## 6. 核查方式

读取 notifications 的 type、target、success、response 和 sent_at 核对投递；业务审批状态、飞书已送达、用户已阅是三件不同的事。脱敏后记录排障结果，不把令牌或真实应用密钥写进文档。

本地可运行 server/test/review-card-sync.test.cjs 和 review-card.integration.cjs；后者使用隔离 PostgreSQL schema 与模拟 HTTP。真实飞书卡片显示仍需发布后单独核验。

## 通知、机器人与手机页面的能力边界

| 能力 | 当前状态 | 详细说明 |
|---|---|---|
| 个人与群主动通知 | 已实现 | [06 通知](06-飞书对接.md)、[19 消息格式](19-飞书通知消息格式.md) |
| 机器人关键词查询 | 已实现，长连接接收消息 | [机器人与移动端](11-飞书接入实战手册.md) |
| LLM 只读工具查询 | 已实现，可配置关闭/回落关键词 | [16 智能体](16-飞书机器人智能体查询方案.md) |
| 多轮对话上下文 | 已实现，bot_conversation 持久化 | 16 篇 |
| 手机 H5 操作与深链 | 已实现，仍须网页地址可达 | [工作台与登录](11-飞书接入实战手册.md) |
| 审核后原卡片状态更新 | 已实现异步回写及重试，有旧消息兼容限制 | 06 篇 |
| 飞书卡片回调直接审批/修改任务 | 未实现 | 当前按钮跳系统页面执行授权操作 |
| 自动绩效评分、自动改任务 | 未实现 | 不从通知或机器人回复推导授权 |

通知是后台主动投递，机器人是用户提问后查询，手机 H5 是用户进入页面操作，三条链路独立。长连接不要求对外暴露事件接收端口；手机打开页面仍要求其网络能访问系统入口。

通知日志使用 notifications，机器人查询日志使用 bot_query_logs，工具追踪用 agent_trace，多轮记录用 bot_conversation。结项待阅/知晓另存 closure_notices；没有实现旧方案设想的 Webhook 管理表和自动失败切换。

机器人所有工具按实际请求人校验权限；LLM 不直接访问数据库，也不提供审批、改任务或提交进展的写工具。项目基础信息可见范围和“查询他人任务”权限不是同一规则。不要复制其他环境用户 ID 或用转发配置替代真实业务身份。

## 通知链接与历史消息兼容

本节根据当前通知生成、卡片回写与前端路由核对；本次未运行数据库或客户端验收。

统一入口更新：侧栏“审批”汇集任务确认、验收、计划变更、结项和重开，支持待我审批、我已审批、我发起的、与我相关及类型筛选。“我的待办 → 待我审批”保留并共用数据。知晓通知分待知晓、已知晓；结项报告页移除待办区。飞书审批通知进入 `/approvals` 并携带具体事项参数，知晓通知进入 `/my-todo?tab=inform&notice=…`；处理后的卡片仍指向原业务记录。

| 通知 | 目标及处理 |
| --- | --- |
| 任务提交验收 | 去审批 → 审批管理 / 待我审批，定位并展开对应任务，查看进展和资料、通过或退回 |
| 验收通过 | 查看验收结果 → 对应任务详情，不再跳项目概览 |
| 验收退回、任务确认退回 | 进入 `/approvals`，分别带 taskId / confirmId 及 at 定位对应审批结果 |
| 已完成任务退回 | 进入 `/tasks?projectId=…&taskId=…` 查看任务并继续处理 |
| 新任务待确认 | 去确认 → `/approvals?confirmId=…`；处理权限仍由后端校验 |
| 变更提交、转终审 | 已有 changeId，进入对应变更并展开；权限和阶段仍由原审批规则控制 |
| 变更通过、退回 | 已有 changeId，查看具体结果；已处理卡片回写时也补齐 changeId |
| 已处理的任务审批卡片 | 回写后进入 `/approvals?taskId=…` 或 `confirmId=…`，附 at 定位该轮结果；历史列表使用 taskLogId |
| 结项会审、终审、退回、撤回、结果 | 已有 request 参数，直接打开对应申请详情；不改成只有项目编号的页面 |
| 项目重开审批及结果 | 已有 request 参数，打开对应结项报告与重开审批 |
| HR 报告通知 | 打开对应结项报告，由页面完成已阅确认 |
| 合理补填知晓、标记撤销通知 | 我的待办 / 待我知晓，定位 notice；飞书按钮改为“查看通知并确认知晓”，避免误解为点击链接即已确认 |
| 单任务周进展缺填 | 保留具体 taskId + weekStart，进入对应周补填 |
| 多任务周进展缺填 | 主按钮打开全部执行待办，各任务的补填链接继续保留对应周；避免主按钮仅打开第一项 |
| 每日个人待办汇总 | 按实际分类选择审批、执行、项目风险或全部；任务验收和变更均属于待我审批 |
| 项目延期、项目/任务计划定稿 | 项目级通知保留项目入口；手机跳转该项目任务列表，保留 projectId |
| 项目群简报 | 项目链接保留具体项目，汇总入口仍到项目总览；群周补填链接保留任务和周次 |

登录重定向保留完整目标地址。手机路由保留任务、周次、变更、申请和通知定位参数；审批还使用 confirmId、taskLogId、at。任务链接在桌面加载后打开详情，无需再次寻找行内入口。

历史消息的原始链接不会因代码发布自动改变；尚在审批卡片同步范围内的消息，后续回写结果时使用新的结果链接。已完成同步的历史卡片不会自动批量重写。

## HR 项目延期日报

项目延期日报对应 `ClosuresService.sendProjectDelayDigest`：查询 active 项目中未完成、未取消的末级任务，按当前截止日期计算自然日延期，卡片每 12 项分片，无延期也发送零项摘要。类型为 `hr_project_delay_daily_N`。这与 08:00 的延期事实留档是不同流程；当前代码没有为该日报配置独立的持久化失败补偿队列。


## 工作日报与已读

工作日报按北京时间的原始提交时间 created_at 汇总，默认上一个工作日；工作日期 work_date 单独显示，不能把补填误当成当天完成。网页仅 admin 或当前总经办接收人可看，普通 leader/dept_head 身份本身不授予权限。读取日报成功后按用户与日期记录已读，未读从首次可见日期开始，不依赖本机浏览器缓存。

工作日 09:00 发送 daily_work_report，按日期与接收人成功记录去重。日报卡片展示最多 30 条摘要，完整内容进入 /daily-report（手机 /mobile/daily-report）；已读不是飞书投递成功，也不代表领导已确认业务结论。
